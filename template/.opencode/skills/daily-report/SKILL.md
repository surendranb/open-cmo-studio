# Standardized Daily Marketing Data Report Protocol

The daily heartbeat of CMO Studio. This is NOT a random metric dump; it is a structured, decision-grade analytical evaluation grounded in the company's verified onboarding stack.

## Operating Principles: No Custom Code, Real Telemetry
1. **Dynamic Platform Discovery:** Checks `workspace_settings` in SQLite (`storage_get_setting('enabled_platforms')` and `storage_get_setting('target_website')`). Only queries platforms the CMO enabled during Onboarding. The studio's own workspace runs the embedded stack below directly (no `enabled_platforms` setting is expected there).
2. **Packaged Analytical Skills:** Uses standard analytical frameworks:
   - `executive-summary-generator`: Top-line BLUF scorecard with WoW rate changes.
   - `metric-reconciliation`: Cross-source sanity checks (e.g. GSC clicks vs GA4 search sessions vs Web logs).
   - `root-cause-investigation`: 5-step causal diagnosis for any metric shift >20%.
   - `data-narrative-builder`: Actionable narrative connecting data to revenue and pipeline.
3. **Provable Truth:** Every figure quotes exact query and period. Blocked or unauthenticated platforms report as `blocked: <reason>` — never fabricated or filled from memory.

## The 8-Part Standardized Report Structure

Every daily data brief follows this strict structure:

### 1. Executive BLUF & Performance Scorecard
- **Top-Line Verdict:** 2-sentence summary of overall health, top gainer, and primary drag.
- **Scorecard Table:**
  | Metric Family | Current 24h/7d | Previous Period | WoW Delta (%) | Health State |
  |---|---|---|---|---|
  | Search Impressions (GSC) | ... | ... | ... | Normal / Surge / Drop |
  | Organic Search Clicks (GSC) | ... | ... | ... | Normal / Surge / Drop |
  | Qualified Site Sessions (GA4) | ... | ... | ... | Normal / Surge / Drop |
  | AI Crawler Visits (Agent Metrics) | ... | ... | ... | Normal / Surge / Drop |
  | Edge Hits (D1 site_requests) | ... | ... | ... | Normal / Scan / Surge |
  | Product / MCP Telemetry (PostHog + Amplitude) | ... | ... | ... | Normal / Surge / Drop |

- **Edge Hits read budget (2026-09-21 law):** exactly ONE 24h D1 pull per report; never `/stats`. Code 7500 (read-cap) → label the row `blocked: read-cap` and carry missing-not-zero.

### 2. Search Visibility & Organic Demand (GSC)
*(Active when `gsc` is in enabled platforms)*
- Top 10 queries by impressions, clicks, CTR, and average position.
- High-intent query gainers (+3 positions) and ranking losses.
- Click-through-rate (CTR) anomalies (high impressions with low CTR = title/meta tag revision opportunity).

### 3. Traffic & User Acquisition (GA4)
*(Active when `ga4` is in enabled platforms)*
- Total Sessions and Active Users over the last 7 days by date.
- Acquisition channel breakdown (Organic Search, Direct, Referral, Social).
- Top 5 landing pages with bounce rate and engagement duration.

### 4. AI Bot Traffic & Machine Readability (Agent Metrics)
*(Active when `agent-metrics` is in enabled platforms)*
- Total crawler hits in 24h via `daily_brief` and `bot_summary`.
- Breakdown by AI crawler family:
  - OpenAI: GPTBot (training) vs ChatGPT-User (search/action)
  - Anthropic: ClaudeBot (training) vs Claude-Web (search)
  - PerplexityBot: Perplexity indexing
  - Google: Google-Extended (Gemini training) vs Googlebot
- Markdown twin adoption (`/{slug}.md` and `llms.txt` requests vs standard HTML).

### 5. Product & MCP Fleet Telemetry (PostHog + Amplitude + CF Analytics Engine & mcp-playbook)
*(Active when `posthog`/`amplitude` are in enabled platforms; the studio's own workspace runs both)*
The studio's MCP servers are our largest products, processing hundreds of thousands of events daily. Grounded in canonical telemetry standards from `surendranb/mcp-playbook`:
- **Store routing (SUR-338, 2026-09-15):** `google-analytics-mcp` (the fleet's largest server, 693k events/mo) reports to **Amplitude** (primary; 2M events/mo free tier) + **Cloudflare Analytics Engine** (`ga4_telemetry` dataset) — its main volume never hits PostHog; PostHog carries only the legacy direct-post strand (`google-analytics`), which is the SAME product: sum it into the product's single row (aggregation law), never print it as a second server. A GA4 main-volume zero-count in PostHog is expected, never an outage. The other 21 gateways report to PostHog (project 489528; roster and event vocabularies live in `config/fleet-gateways.json`). The fleet table is generated by `python3 scripts/fleet-telemetry.py` — paste it, never rebuild it by hand. Amplitude read: Dashboard REST Segmentation API (`https://amplitude.com/api/2/events/segmentation`, Basic `AMPLITUDE_API_KEY:AMPLITUDE_SECRET_KEY` from Keychain service `agent-core`); Rows > 0 is strictly computed as `tool_calls - zero_row_calls` (eliminating the 'blocked' status loophole when direct `rows_returned > 0` segmentation returns 400). CF AE SQL reads blocked until an Account Analytics token exists (verified 2026-09-20).
- **Cap-metric law (SUR-349, 2026-09-22):** the cap watch = ALL event types the edge forwards to Amplitude (`tool_executed` + `mcp_started` + `tools_listed` + `skill_tip_shown` + `session_end` + tail). `tool_executed` alone (≈4% of all-events) is a usage lens, never the cap lens — never quote a cap % without naming the scope. Baseline: 09-21 = 42,763 events/day ≈ 64% of the 2M/mo run-rate (4-day avg 33,075 ≈ 50%).
- **Amplitude metric law (2026-09-23 — burned us once):** the Segmentation API defaults to `uniques`; every volume pull sets `m=totals` explicitly. Morning 09-23 reported tool_executed uniques (174) as calls against a 1,556 partial-day anchor — true totals were 2,036 calls / 18,635 boots. Equality-check every pull against the prior anchor (partial-day run-rate or finalized day) before publishing; a 5x+ gap means wrong metric, not a real move. One event per call (API honors only the last `e`).
- **Amplitude filter law (SUR-349):** segmentation filters bind ONLY nested inside `e` (`e={"event_type":"…","filters":[…]}`); top-level `g=`/`group_by=` silently return the unfiltered series. Equality-check before trusting any filtered series (2026-09-22: unfiltered `[567,727,1885,1556]` ≠ `status=success` `[524,618,1747,1452]` ≠ `rows_returned=0` `[95,165,298,269]`).
- **Per-Server Telemetry Table** (plain-language standard, 2026-09-23 principal order):
  | Server | Install | Boots | Tool calls | Rows > 0 | Intent known | Errors |
- **Column definitions**: Install = new installs; Boots = process starts; Tool calls = tool executions; Rows > 0 = tool calls that returned data (strictly computed as `tool_calls - zero_row_calls`, eliminating the 'blocked' status loophole); Intent known = tool calls carrying the caller's intent (prove the property per server before quoting; `not captured` where a server never sends it); Errors = failed tool calls. Counts only — no rate columns and no "delivery" wording in any principal-facing table.
- **Full-data law (2026-09-23, principal order):** every server with a non-zero in ANY column (install, boots, tool calls, rows > 0, intent known, errors) gets its own full row — never folded into `rest` / `others` / `remaining`. A count of 1 is data, not noise; aggregation hides exactly the servers that need attention (2026-09-23: a `rest` row buried 5 fresh installs across 4 silent servers). Zero-everywhere servers print one `silent` row so silence is witnessed, not assumed.
- **Name-and-domain law (2026-09-23, principal order):** fleet rows carry the telemetry `mcp_server_name` VERBATIM — never paraphrased (`google-analytics (residual)`, `null-name` are banned; write `google-analytics`, `(none) — unstamped, installer funnel`). Website rows are labeled by DOMAIN, never by property nickname: builditwithai.xyz (not "studio"), surendranb.com (not "suren"), freeinference.dev (not "FI"), fdejobsboard.com (not "fde"), ga4mcp.com. Dashboards already key GSC by domain (`gsc_daily`); GA4 rows carry the property→domain map alongside.
- **Aggregation law (2026-09-23, principal order — supersedes the two-row treatment):** one product = ONE row. A product reporting to two stores is combined into a single row before it reaches the table — never printed as two. google-analytics-mcp = Amplitude (edge-forwarded) + its PostHog legacy strand (`google-analytics`), summed. Combine only disjoint populations (edge cutover splits them by construction), on matching windows where possible; where windows differ, label the row plainly (one line, no codes) and flag the mismatch — never mix silently. Store detail lives in the brief/artifacts, never as extra rows in the note. A server is never skipped because it lives in the other store.
- **macos-mcp boots-only law (2026-09-23, code-verified):** macos-mcp emits only `server_first_install` + `mcp_started` by construction (`macos-mcp/src/telemetry.ts` has no `tool_executed` hook; the tool dispatch in `src/index.ts` is unwrapped) — its calls/active cells read `n/a (boots-only instrumented)`, never `0`, and boots-high-calls-unobservable is never an anomaly. `active = uniq(distinct_id)` over call events, so 0 active is instrument artifact. Its boots arrive with client `unknown` (`trackMcpStarted` called without clientInfo) and feed the unstamped `(none)` blob. Boots = stdio process starts (one per client session), not users. The omission is privacy-deliberate (server touches Mail/Calendar/Notes/clipboard/camera) — adding call tracking is a principal decision, never an analyst default.
- **Rows > 0 standard**: strictly computed as `tool_calls - zero_row_calls` (eliminates the 'blocked' status loophole). A call returns rows when data is delivered (`status = success AND rows_returned > 0`); empty success does not count. Shares/rates are internal analysis only — never a note column.
- **Top Error Triage**: Rank by affected installs (`uniq(distinct_id)`), not raw error events to prevent retry-loop skew.
- **Harness Breakdown**: Distribution across `claude-code`, `claude_cowork` (local-agent-mode), `claude-ai`, `cursor`, `codex`, `other`.
- **Raw Dump**: Always written to `memory/daily/<YYYY-MM-DD>/artifacts/telemetry/mcp-fleet-<YYYYMMDD>.json`.
- **GitHub traffic law (2026-09-23, principal order):** views/clones/referrers are NEVER "token-blocked" — read `~/Projects/mcp-playbook/github-traffic/` directly: `daily.csv` (date,repo,clones,unique_cloners,views,unique_visitors — settled days only), `stats.csv` (per-run 14d window totals incl. stars/forks — window uniques can't be rebuilt by summing daily rows), `referrers.csv` (top-10 referrers per repo per run). Staleness travels on every figure (dataset settled through 09-10 daily / 09-13 stats; the updater needs `gh` auth, broken locally since 09-14 — so post-09-10 is missing-not-zero). Stars/forks also readable live via unauth `api.github.com`.

### 6. Metric Cross-Reconciliation
*(Powered by `metric-reconciliation` skill)*
- Compares overlapping measurements across sources:
  - GSC Organic Clicks vs GA4 Organic Search Sessions.
  - Server Log Crawler Visits vs GA4 Bot Exclusions.
  - D1 edge per-host reqs vs GA4 sessions (D1 must be ≥ GA4 — it sees bots + no-consent hits GA4 drops).
  - D1 probe paths (`/wp-signup.php`, `/wp-login.php`, `.env/.git`) vs Agent Metrics top paths (must agree on flood days).
- Discrepancy explanation table with confidence tags:
  | Metric Comparison | Source A | Source B | Delta (%) | Reconciliation Mechanism |
  |---|---|---|---|---|
  | Search Traffic | GSC: X clicks | GA4: Y sessions | Z% | Attribution lag, redirect drops, or consent banner bounce |

### 7. Anomaly Root Cause Analysis
*(Powered by `root-cause-investigation` skill)*
For any metric deviating >20% from 7-day baseline, apply the 5-step diagnostic framework:
1. **Observed Anomaly:** Baseline vs actual with exact timeframe.
2. **Change Candidates:** Correlated releases, site changes, ranking drops, bot flood events, or tracking disruptions.
3. **Mechanism:** Direct causal chain linking change candidate to observed metric shift.
4. **Cascaded Impact:** Downstream effect on conversions, user trust, or indexing.
5. **Label & Falsifier:** `[Fact]` / `[Inference]` / `[Hypothesis]` + "This conclusion is invalidated if <X>".

### 8. WHAT WE SHOULD DO (The 3 Marketing Commitments)
Never an observation dump; max 3 concrete actions:
- **ACTION:** Specific, measurable task to execute today.
- **EVIDENCE:** The exact numbers from this run justifying the action.
- **EXPECTED IMPACT:** Measurable metric movement expected.
- **OWNER:** cmo (agent executes) / principal (requires human decision or API key) / builder (technical fix).

## 9. Dashboard update (`dashboard/` — metrics + narrative, Evidence-compatible)

The brief is the day's snapshot; `dashboard/` is the maintained memory. Every run upserts the same numbers into both.

1. **Dispatch rows:** data-analyst returns include CSV-ready rows for every pulled table (daily grains + window grains + scorecard + commitments).
2. **GitHub history first:** `python3 dashboard/scripts/sync_github_history.py` (merges settled fleet history + our pulls), then upsert (cmo, idempotent): `python3 dashboard/scripts/append_daily.py --file <name> --row "..."` — same-key re-pulls replace, history is never deleted. Keys per file in the script's `KEYS`.
3. **Narrative:** append the brief link to `dashboard/pages/archive.md`; update standing reads on the touched pages only when the verdict changed (cite the run).
4. **Rules:** missing dates stay missing (never interpolate/zero-fill); `trusted=false` GSC rows never leave the dashboard (`brand_watch`/`gsc_summary` carry the flag); no secrets in CSVs.
5. **Regenerate:** `python3 dashboard/scripts/build_evidence.py --validate` (loads CSVs into local PG with exact-count checks + validates pages, must pass 0 errors) + `python3 dashboard/scripts/build_preview.py` (offline fallback) and commit both with the run.
6. **Commit** dashboard + brief + work doc together.
